# ComputeOperation

A `ComputeOperation` describes a single compute op to be executed on the
Spyre device. It specifies the execution unit (SFP or PT), the operation
function name, optional attributes, and the input/output tensors from
`labeledDs_` that the operation reads and writes. More than one
`ComputeOperation` can appear in `computeOp_` for fused operations.

## Context

`ComputeOperation` entries appear in the `computeOp_` array inside each
[`DesignSpaceConfig`](designspaceconfig.md). Tensor references in
`inputLabeledDs` and `outputLabeledDs` use the composite name
`"<dsName_>-idx<ldsIdx_>"` defined in
[`LabeledDataStructure`](labeleddatastructure.md).

```json
"computeOp_": [
  { <ComputeOperation> },
  ...
]
```

## Structure

```json
{
  "exUnit":                          "sfp" | "pt",
  "opFuncName":                      "<string>",
  "attributes_":                     <OperationAttributes>,
  "location":                        "Inner" | "Outer",
  "inputLabeledDs":                  [<string>, ...],
  "outputLabeledDs":                 [<string>, ...],
  "indirectAccessIndexLabeledDs_":   [<string>, ...],
  "interimLabeledDs_":               [<string>, ...]
}
```

## Fields

All four required fields must be present. No additional properties are allowed.

| Field | Type | Required | Constraints | Description |
|---|---|---|---|---|
| `exUnit` | string enum | Yes | `"sfp"` `"pt"` | Execution unit. `"sfp"` = Spyre Floating Point unit; `"pt"` = Processing Tile array. |
| `opFuncName` | string | Yes | — | Operation function name as generated by torch-spyre. See [Supported Operations](#supported-operations). |
| `attributes_` | object | No | — | Optional operation attributes. See [attributes_ sub-fields](#attributes_-sub-fields) below. |
| `location` | string enum | No | `"Inner"` `"Outer"` | Placement in the schedule loop nest. `"Inner"` = op executes inside the innermost loop; `"Outer"` = op executes in an outer loop. |
| `inputLabeledDs` | array of string | Yes | — | Input tensor references from `labeledDs_` using the `"<dsName_>-idx<N>"` naming convention. |
| `outputLabeledDs` | array of string | Yes | — | Output tensor references from `labeledDs_` using the `"<dsName_>-idx<N>"` naming convention. |
| `indirectAccessIndexLabeledDs_` | array of string | No | — | Index tensors for indirect access operations (gather/scatter). See `ScheduleTreeNode.indirectAllocType_`. |
| `interimLabeledDs_` | array of string | No | — | Intermediate tensors used within the operation, not exposed as inputs or outputs. |

### attributes_ sub-fields

| Field | Type | Required | Constraints | Description |
|---|---|---|---|---|
| `dataFormat_` | string | No | — | Data format for this operation (e.g. `"SEN169_FP16"`). |
| `fidelity_` | string | No | `"regular"` `"high"` `"low"` | Computation fidelity level. |

**Note on field naming:** `exUnit`, `inputLabeledDs`, and `outputLabeledDs` lack the trailing
underscore used by most other fields. `SDSC-json-api.md` refers to them as `exUnit_`,
`inputLabeledDs_`, and `outputLabeledDs`. The serialized keys in the JSON bundle are
`exUnit`, `inputLabeledDs`, and `outputLabeledDs` (no trailing underscore) — this
inconsistency is a known anomaly. Do not add trailing underscores when writing bundle JSON.

## Example

The example below shows a GELU operation and the `labeledDs_` entries it references.
Tensor names follow the `"<dsName_>-idx<ldsIdx_>"` convention.

```json
"labeledDs_": [
  {"ldsIdx_": 0, "dsName_": "gelu-Tensor0", "dsType_": "INPUT",  "dataFormat_": "SEN169_FP16", "memOrg_": {"hbm": {"isPresent": 1}, "lx": {"isPresent": 0}}},
  {"ldsIdx_": 1, "dsName_": "gelu-Tensor1", "dsType_": "OUTPUT", "dataFormat_": "SEN169_FP16", "memOrg_": {"hbm": {"isPresent": 1}, "lx": {"isPresent": 0}}}
],
"computeOp_": [
  {
    "exUnit": "sfp",
    "opFuncName": "gelufwd",
    "attributes_": {
      "dataFormat_": "SEN169_FP16",
      "fidelity_": "regular"
    },
    "location": "Inner",
    "inputLabeledDs":  ["gelu-Tensor0-idx0"],
    "outputLabeledDs": ["gelu-Tensor1-idx1"]
  }
]
```

`"gelu-Tensor0-idx0"` is formed by concatenating `dsName_` (`"gelu-Tensor0"`) with
`-idx` and `ldsIdx_` (`0`).

## Supported Operations

The full list of operations that torch-spyre can generate is documented in the
[torch-spyre documentation](https://torch-spyre.readthedocs.io/).
